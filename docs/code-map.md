# Code map

What each part owns, who calls whom, and how a Windows-only app becomes Windows + Linux + a Decky plugin (SPEC M6-M9), with a command line on top. Describes commit: `f86f36e` (2026-11-05). Checked against `main` on 2026-11-07: every module in the repo root, `qt_platform/` and `decky/` is listed below; 848 unit tests pass on Linux (with #62, after #86 and the MCP server, #75, the disconnect race #103, and the error-path restore #116). Spec: [../SPEC.md](../SPEC.md). Background and measured facts: [notes/](notes/).

## Layout

"Wired" means the running app (window, `qtetherd`, CLI) calls it; "not wired yet" means it is merged and tested but nothing calls it, and the issue named wires it in.

| Path | Owns | State | Musts |
|---|---|---|---|
| `adb_manager.py` | `ADBManager`: find adb, list devices, find the Quest, device details, start/stop the gnirehtet client on the headset (an `Error` line in the `am start` reply, read by `am_result`, means the intent was refused, #63; the headset is woken with `keyevent 224` before the start and stop intents, #64), VPN up/down, the VPN agent's state from `dumpsys` (diagnostic, #64), the headset's awake state from `dumpsys power` (`is_headset_awake`, `device_listed`: the serial in `adb devices -l` in any state, None when the call fails, #65), `tun0` stats, Wi-Fi toggle, USB monitor loop (`_monitor_step`, one poll: fires connected for a new serial and once more when a known serial goes from unauthorized to device, so accepting the USB debugging prompt reaches the connect path, #109). | wired | M1, M2, M5 |
| `tether_manager.py` | `TetherManager` + `TetherState` + `TetherStats` + `temperature_zone`: the relay process, connect/disconnect, health monitor (awake-gated liveness from `heal_policy` decides when a restart is due, `heal.Healer` picks the rung, #65), auto-reconnect (`reconnect_count` counts outages, not attempts, #79; a connect while Connecting, Connected or Reconnecting is refused, so a replug never starts a second relay, #86), split relay mode (#66: `relay -p` alone, a port wait, a port held by another program is refused and never killed, then the client start; `QT_RELAY_MODE=run` keeps `gnirehtet run` for A/B), stats, battery level and temperature on one `dumpsys battery` poll (#4), Connected only once `tun0` is up (#1), the headset Wi-Fi policy. Relay output (#62): the relay's stdout is a pipe that `relay_pump` drains on a thread; each `Client #N connected/disconnected` line updates `stats.relay_clients` (None until the relay prints one this spawn). Once it has, Connected also needs at least one counted client (`_state_for_tunnel`, the one gate for connect, health check, heal and reconnect); a relay that never prints one falls back to `tun0` alone. Each spawn and kill bumps a generation, so a line from an old relay is ignored. The health check (`_check_tunnel`, #102) takes the same gate: tun0 up with a counted zero clients is not a live tunnel, so it takes the missing-tunnel branch and the awake-gated heal re-issues the client start, instead of staying Starting. Disconnect stops the VPN on the headset first and waits up to 6 s for `tun0` to go (force-stop on timeout), then Wi-Fi, reverse tunnels and the relay, in that order, with the relay killed even on failure (#64). `disconnect(headset_present=False)` (#86) skips every headset-side step and only stops the health thread and the relay, for a cable that is already out. `force_kill` (quit) sends a bounded STOP first. One health loop per tether (#108): a relay death with auto-reconnect off stops the loop (`_running` False) along with the Error state, and `_start_health_monitor` gives a loop left from the last session up to 2 s to exit, then keeps it (following the new serial) rather than start a second; disconnect keeps the handle of a loop that outlives its 5 s join. Once a started session is stopped (`_stop_requested`: connect has run, `_running` is False, #103), reconnect and heal return before the next relay spawn, client start or Connected state, and disconnect owns the relay and the state. `_relay_died`, `_check_tunnel` and `_give_up_healing` also return at once after a stop (#116), so a death or give-up seen during disconnect never sets Error over Stopping or Idle. The error exits that leave the headset VPN up (a relay death with auto-reconnect off, `_give_up_healing`, the max-attempts exit of `_attempt_reconnect`) first call `_restore_headset_best_effort` (#116): the STOP intent, a bounded wait for `tun0` (2 s, force-stop once), then a Wi-Fi toggle and one connectivity check, with 2 s caps, skipped when the headset is not listed, and it never raises. Each exit goes through `_end_in_error`, which keeps its Error state and message, unless a disconnect() came in during the restore: then the restore stops between steps and the disconnect owns the state (`_disconnect_count`). The relay spawn and kill run under `_proc_lock` (`_spawn_relay_if_live`, `_kill_process`), so a relay that starts during a stop is killed at once and never left behind. Connect checks for a stop after each blocking step (`_connect_stopped`: after the relay start, each tun0 poll, the device details, before Connected, before and after the Wi-Fi policy): a stop returns with no state set and kills a relay this connect left behind, while a superseded connect returns without a kill (#115). A stop that lands inside the Wi-Fi policy makes connect() put the headset Wi-Fi back (`restore_wifi_if_flagged`), since disconnect() may already have restored it before the policy's adb calls ran. Each connect() bumps `_session_gen` (before `_running` turns True, so a kept loop never sees the old generation beside a running session) and hands the health loop over by setting `_health_active_gen` just before `_start_health_monitor`; a loop kept from an older session idles (`_health_session_current`) until then, so it cannot heal beside the new connect. The tether core. | wired (OS calls go through `qt_platform.current()`) | M1-M5 |
| `heal.py` | `Healer`: the pure heal ladder plus two breakers, the flap breaker and the reconnect cap (#46). `now` is passed in, nothing sleeps. `escalate(now)` takes the next rung at once (the liveness policy decides when, #65); `observe()` is the miss-count path. Each returns a `Heal`: `NONE`, `RESTART_CLIENT`, `RESTART_ADB_THEN_CLIENT`, `FULL_RECONNECT` or `GIVE_UP`, and `trip_reason` (`"flap"` or `"reconnects"`) says which breaker tripped. `TetherManager` runs with `flap_max=None` (flap breaker off), so only the reconnect cap can give up. | wired (`tether_manager`) | M2 |
| `heal_policy.py` | Pure awake-gated liveness policy: wakefulness parse, restart backoff (60 s doubling to 300 s), `Liveness` transitions. The health loop restarts only after the headset has been awake and tun0 silent for the 10 s grace; asleep silence never restarts. Any tun0 read restarts the silence and awake clocks; tun0 back for 10 s also resets the restart count. A missing headset reading is not awake and clears the awake clock; 15 s of no reading (`UNREADABLE_GRACE`) with the headset still listed in adb in any state (offline and unauthorized lines count, a failed `adb devices` call counts as a wedged adb) allows a restart that starts with the adb-server restart, under the same backoff and cap, while an unplugged headset keeps waiting (#86). The restart is recorded even when the heal raises. Relay deaths wait out the same backoff (#65). | wired (`tether_manager`, `adb_manager`) | M2 |
| `relay_log.py` | Pure parser: relay "Client #N connected/disconnected" lines and the connected-client set (#62). | wired (`relay_pump`, `tether_manager`) | M1 |

## Who calls whom

```mermaid
flowchart LR
  subgraph Windows
    WinUI[main.py window + tray] --> CoreW[TetherManager / ADBManager]
  end
  subgraph Linux
    LinUI[main.py window + tray] -->|JSON on 127.0.0.1| D[qtetherd.py]
    Decky[decky/ Quick Access panel] --> DB[decky/main.py backend] -->|JSON on 127.0.0.1| D
    D --> CoreL[TetherManager / ADBManager]
  end
  CLI[cli.py + cli_commands.py] -->|service answers| D
  CLI -->|no service| CoreW
  CLI -->|no service| CoreL
  MCP[mcp_server.py: quest-tether mcp, stdio] --> CLI
  CoreW --> P[qt_platform.current()]
  CoreL --> P
  CoreW --> Sync[net_sync.py] --> P
  CoreL --> Sync
  CoreW --> Heal[heal.py]
  CoreL --> Heal
  P --> Tools[(tools/: adb, relay, APK)]
```

- On Windows nothing changes in shape: the window runs the core in-process.
- On Linux the service owns the relay, so the desktop window and Game Mode can't start two relays fighting over port 31416 (the bug the Windows mutex fixed). It runs as a systemd user unit, started at login. If `request({"cmd": "status"})` gets no answer when the window starts, the window runs the old in-process core. Once running, it takes the core over only when the port is refused (service gone, `_reprobe_service` in `main.py`); a slow or busy service leaves it a client.
- The Decky backend never runs adb or the relay itself; it only forwards status / connect / disconnect.
- The CLI talks to the same service for status, connect, disconnect, wifi-sync, logs and settings when it answers; otherwise (Windows, or no service) it runs `TetherManager` in-process (the owner's ruling, 2026-11-04). The MCP server (#75) sits on the same `cli_commands` layer, so Claude Code gets the same answers as the CLI.
- Crash reports: `crash_hook` catches uncaught exceptions in the window and the service and hands them to `crash_report`, which scrubs, limits, queues and uploads in the background.

## Mac, PC and Linux

- **Windows:** today's app. Keeps the Java relay (Rust relay carries no traffic there, #9).
- **Linux (desktop and SteamOS):** the same window and tray (Tk and pystray work on Linux; pystray needs an AppIndicator on KDE/SteamOS), native relay, NetworkManager for Wi-Fi sync, USB access through a udev rule for the headset's vendor id. The Linux package installs the rule at install time with one visible sudo prompt and removes it on uninstall (the owner's ruling, 2026-10-26: "Install with the package"); the app never asks for root after that.
- **SteamOS Game Mode:** the Decky plugin only (no window).
- **Mac:** not supported (SPEC Won'ts).
- **CI:** `.github/workflows/check.yml` byte-compiles everything (`compileall`) and runs `tests/` on Windows and Linux, on GitHub-hosted runners (`windows-latest`, `ubuntu-latest`); push to `main` and every pull request. No Mac job, by design.
